# Clothing Store Product Catalog: Design Spec

- **Date:** 2026-11-09
- **Status:** Approved in brainstorming, awaiting written-spec review
- **Repos:** `ProductCatalogService` (this repo, Spring Boot 4) and a new `clothing-storefront` repo (Next.js)

## 1. Goal and scope

A product catalog for a real clothing store that is launching soon. Customers browse products by category, view detailed product pages, and search with typo-tolerant full-text search. Staff manage the catalog through simple admin pages.

### Requirements

1. Customers can browse products by category.
2. Product detail pages show images, description, specifications, and size/color variants with stock and price.
3. Customers can search products by keyword.
4. Staff can manage product listings, details and categories.
5. MySQL is the system of record.
6. Elasticsearch provides fast full-text search with typo correction.

### In scope

- The catalog microservice (this repo), extended rather than rewritten.
- A Next.js storefront and admin pages that consume the catalog APIs.
- Deployment, security, operations and testing needed for a production launch.

### Out of scope (separate later projects)

- **User management service.** It owns staff accounts, login, password storage and roles, and issues signed JWTs. The catalog only validates these tokens.
- Cart, checkout, orders, payments and customer accounts.
- Multiple currencies and multiple languages. The catalog uses one currency and English only.

### Expected scale

1,000 to 50,000 products in the first year, not counting variants.

### Principles

- **MySQL is the only source of truth.** The Elasticsearch index is a copy and can always be rebuilt from MySQL.
- **Product detail pages and the category tree read from MySQL**, so price and stock are current.
- **Category listings and search read from Elasticsearch**, because they need filter counts. If Elasticsearch is unavailable, category listings fall back to MySQL (see 5.6).
- **Image files never pass through the catalog service.** It issues pre-signed upload URLs and stores only image URLs.
- **The catalog never calls the user service at request time.** It verifies JWT signatures against the user service's public keys (a JWKS URL).

## 3. Data model (MySQL)

All tables have `created_at` and `updated_at`. IDs are `BIGINT AUTO_INCREMENT`, generated by the database. The schema is managed only by Flyway migrations; `spring.jpa.hibernate.ddl-auto` is set to `validate`.

| Table | Columns | Constraints and notes |
|---|---|---|
| `category` | id, parent_id (nullable FK → category), name, slug, description, image_url, sort_order, status `ACTIVE/INACTIVE` | `slug` unique. Categories form a tree of any depth. |
| `product` | id, slug, title, description (Markdown), brand, category_id (FK), base_price `DECIMAL(10,2)`, status `DRAFT/PUBLISHED/ARCHIVED`, published_at, version | `slug` unique. `version` is used for optimistic locking. Indexes on (category_id, status) and (status, published_at). |
| `product_variant` | id, product_id (FK), sku, size, color, color_hex, price_override `DECIMAL(10,2)` (nullable), stock_quantity, status `ACTIVE/INACTIVE` | `sku` unique; (product_id, size, color) unique; stock_quantity ≥ 0. The effective price is `price_override` if set, otherwise `base_price`. |
| `product_spec` | id, product_id (FK), name, value, sort_order | Specifications such as Material, Fit, Care. |
| `product_image` | id, product_id (FK), color (nullable), url, alt_text, sort_order | `color` set: the image belongs to that color's variants. `color` null: the image applies to all colors. |
| `search_outbox` | id, product_id, operation `UPSERT/DELETE`, attempts, next_attempt_at, last_error, status `PENDING/DONE/FAILED`, created_at, processed_at | Index on (status, next_attempt_at). |

### Business rules

- A product can be published only if it has a category, a title, a base price above 0, at least one active variant, and at least one image.
- Products are never hard-deleted; they are archived. Variants, specs and images can be deleted.
- A category with products or subcategories cannot be deleted (409).
- Only `PUBLISHED` products are visible through public APIs. Draft and archived products return 404.

### Changes to existing code

- Replace `double` prices with `BigDecimal` / `DECIMAL(10,2)`.
- Generate IDs in the database. Remove client-supplied IDs and the "already exists" check in `createProduct`.
- Remove `FakeStoreProductService`, `FakeStoreProductDto`, the `@Primary` workaround, and the `spring-boot-starter-restclient` dependency if nothing else uses it.
- Remove `Product.isSaleSpecific`, `Product.sku` and `Product.stockQuantity`. SKU and stock move to `product_variant`.
- Replace the `/products` endpoints with `/api/v1/...`. Nothing outside this repo calls them.
- Move the datasource password and all other secrets to environment variables. **Rotate the MySQL password that was committed to git history.**
- Keep the existing `controllers` / `services` / `repos` / `dtos` / `models` package layout. Public and admin APIs use separate DTOs.

## 4. API

All paths are prefixed with `/api/v1`.

### 4.1 Public APIs (no auth)

| Method & path | Returns | Data source |
|---|---|---|
| `GET /categories` | Full tree of ACTIVE categories | MySQL |
| `GET /categories/{slug}` | Category, breadcrumbs, direct children | MySQL |
| `GET /categories/{slug}/products` | Products in the category and its subcategories, with filter counts | Elasticsearch (MySQL fallback) |
| `GET /products/{slug}` | Product detail: description, specs, images, active variants with effective price and stock, breadcrumbs | MySQL |
| `GET /search?q=` | Ranked results, filter counts, `didYouMean` | Elasticsearch |
| `GET /search/suggest?q=` | Up to 8 autocomplete suggestions (product titles and category names); requires `q` of at least 2 characters | Elasticsearch |

Listing and search endpoints accept these query parameters:
- `size`, `color`, `brand`: repeatable
- `minPrice`, `maxPrice`, `inStock`
- `sort`: one of `relevance` (search only, the default for search), `newest` (the default for categories), `price_asc`, `price_desc`
- `page`: 0-based
- `pageSize`: default 24, maximum 100

### 4.2 Admin APIs (JWT required)

| Area | Endpoints | Role |
|---|---|---|
| Categories | `GET/POST /admin/categories`, `GET/PUT/DELETE /admin/categories/{id}` | ADMIN |
| Products | `GET /admin/products?status=&q=&page=` (searches title or SKU), `POST /admin/products`, `GET/PUT /admin/products/{id}`, `POST /admin/products/{id}/publish`, `POST /admin/products/{id}/archive` | EDITOR, ADMIN |
| Variants | `POST /admin/products/{id}/variants`, `PUT/DELETE /admin/variants/{id}`, `PATCH /admin/variants/{id}/stock` | EDITOR, ADMIN |
| Specs | `PUT /admin/products/{id}/specs` (replaces the full list) | EDITOR, ADMIN |
| Images | `POST /admin/products/{id}/images/upload-url`, `POST /admin/products/{id}/images`, `PUT /admin/products/{id}/images/order`, `DELETE /admin/images/{id}` | EDITOR, ADMIN |
| Search ops | `POST /admin/search/reindex`, `GET /admin/search/status` | ADMIN |

- `PUT /admin/products/{id}` must include the `version` it read. A stale version returns 409.
- Upload URLs expire after 5 minutes and accept only `image/jpeg`, `image/png` or `image/webp`, up to 10 MB.

### 4.3 Conventions

- **Errors** use `ProblemDetail` (RFC 9457):
  - 400: validation, with field errors
  - 401: missing or invalid token
  - 403: wrong role
  - 404: not found
  - 409: duplicate slug or SKU, stale version, delete blocked, publish rules not met (with the reasons listed)
  - 503: search unavailable
  - 500: generic message; the stack trace is never included
- **Paged responses** have the form `{ items, page, size, totalItems, totalPages }`. Listing and search responses also include `facets`, and search responses include `didYouMean`.
- **Slugs** are generated from the name or title when not supplied and must be unique.

### 4.4 Authentication

- The catalog is a Spring Security OAuth2 resource server.
- It validates JWT signatures against a JWKS URL configured by `CATALOG_JWT_JWKS_URI`, and reads the role from the `roles` claim.
- In local and test environments, a dev signing key is configured instead, so tokens can be minted without the user service. Switching to the real user service is a config change only.
- CORS allows only the storefront origin.

## 5. Search

### 5.1 Index

- The app reads and writes through the alias `products`, which points at a versioned index (`products_v1`, `products_v2`, …).
- Each document represents one product. Only `PUBLISHED` products are indexed.

| Field | Type | Purpose |
|---|---|---|
| id, slug | keyword | identity, links |
| title | text (english analyzer + synonyms), plus `search_as_you_type` and shingle subfields | matching, autocomplete, did-you-mean |
| brand | text + keyword | matching, filter |
| description, specsText | text (english) | matching |
| categoryNames | text | matching |
| categoryIds | long[] (own category plus all ancestors) | category browsing that includes subcategories |
| colors, sizes | keyword[] (from in-stock active variants) | filters and counts |
| minPrice, maxPrice | scaled_float (factor 100) | price filter and sort |
| inStock | boolean | filter, ranking boost |
| primaryImageUrl | keyword (not indexed) | display |
| publishedAt | date | `newest` sort |

### 5.2 Matching and relevance

- **Analysis:** an english analyzer for stemming, plus a synonym filter loaded from a synonym file. Initial synonyms: tee/t-shirt/tshirt, jeans/denim, hoodie/sweatshirt, trainers/sneakers.
- **Query:** `multi_match` with these field weights: title ×3; brand and categoryNames ×2; colors and specsText ×1; description ×0.5.
- **Typo tolerance:** `fuzziness: AUTO`, `prefix_length: 1`.
- **Ranking boost:** a small boost for `inStock: true`.
- **Filters** go in filter context, so they never affect scoring.
- **Filter counts:** aggregations on sizes, colors and brand, plus price ranges. A selected facet's own filter is applied through `post_filter`, so the counts for its other values stay visible (multi-select facets).
- **Did you mean:** a phrase suggester on the title shingle field. The suggestion is returned when total hits are below 5.
- **Autocomplete:** a `bool_prefix` query on the title `search_as_you_type` field, plus category names.

### 5.3 Outbox indexer (sync option 1)

1. **Writing outbox rows.** Every product-affecting write inserts a `search_outbox` row in the same transaction. That covers product, variant, spec, image, stock and publish/archive changes. A category rename or move inserts rows for every product in that category and its subcategories.
2. **Polling.** A `@Scheduled` job runs every 1 second. It claims up to 100 rows with `status=PENDING AND next_attempt_at <= now()` using `SELECT … FOR UPDATE SKIP LOCKED`, so several service instances never claim the same row.
3. **Building documents.** Claimed rows are de-duplicated per product. Each document is rebuilt from current MySQL state, so processing is idempotent.
   - If the product is `PUBLISHED`, the document is upserted.
   - Otherwise, it is deleted from the index.
4. **Sending.** All changes go to Elasticsearch in one Bulk API call. Successful rows are marked `DONE`.
5. **Retrying.** On failure, `attempts` is incremented and `next_attempt_at` is set with exponential backoff (2^attempts seconds, capped at 10 minutes). After 10 attempts, the row becomes `FAILED` and is listed in `/admin/search/status`.
6. **Cleanup.** A daily job deletes `DONE` rows older than 7 days.

### 5.4 Full reindex

1. Create `products_vN+1` with the current mapping.
2. Bulk-index all `PUBLISHED` products from MySQL in batches of 500.
3. Atomically move the `products` alias to the new index.
4. Delete the old index.

The outbox keeps running throughout, so edits made during a reindex are applied afterwards. Only one reindex can run at a time; a second request returns 409.

### 5.5 Client

Spring Data Elasticsearch (Elasticsearch 9). Use Elastic Cloud or a self-hosted node, **not** AWS OpenSearch Service, which is an incompatible fork.

### 5.6 Degraded mode

When Elasticsearch is unreachable:
- `/search` and `/search/suggest` return 503.
- `/categories/{slug}/products` falls back to a MySQL query with sorting and paging but no filter counts. The response includes `degraded: true`.
- Product detail pages and admin writes are unaffected. The outbox builds up and catches up when Elasticsearch returns.

## 6. Next.js app (`clothing-storefront` repo)

Next.js App Router, TypeScript, Tailwind. Designed mobile-first.

### 6.1 Storefront

| URL | Content |
|---|---|
| `/` | Featured categories, new arrivals |
| `/c/[...slug]` | Breadcrumbs, product grid, filters (sidebar on desktop, bottom sheet on mobile), sorting, pagination. Filters are kept in URL query params. |
| `/p/[slug]` | Image gallery that changes with the chosen color; size and color pickers; effective variant price; stock status ("Only N left" when N ≤ 5; out-of-stock options disabled); specs table; Markdown description rendered safely; breadcrumbs; "Add to cart" button disabled until the cart service exists |
| `/search?q=` | Results grid, filters, "Did you mean" link, empty state suggesting categories |
| Header search | Autocomplete with 200 ms debounce; Enter goes to `/search` |

### 6.2 SEO

- Server rendering, with title, description and Open Graph tags on every page.
- JSON-LD `Product` data with price and availability.
- `sitemap.xml` generated from published products and categories, plus canonical URLs.
- Real 404 for missing, draft or archived products.

### 6.3 Caching

- Category and product pages: `revalidate: 60` seconds.
- Search: never cached.
- Images: served through `next/image` from the CDN.
- Stock shown on product pages can be up to 60 seconds old. The future cart and checkout service must re-check stock when an order is placed.

### 6.4 Admin (`/admin`, `noindex`)

| Page | Capabilities |
|---|---|
| Product list | Filter by status, search by title or SKU |
| Product editor | Basic info, category picker, spec rows (add, remove, reorder), variant generator (choose sizes × colors, then edit SKU, stock and price per combination), drag-and-drop image upload with color tagging and reordering, Publish/Unpublish showing the 409 reasons |
| Categories (ADMIN) | Tree editor: add, rename, move, reorder |
| Search status (ADMIN) | Outbox backlog, failed rows with errors, Reindex button |

- The JWT is stored in an httpOnly, Secure, SameSite=Lax cookie.
- Admin API calls go through Next.js server-side route handlers that attach the token. Browser JavaScript never sees the token.
- Until the user service exists, a dev-only login issues test tokens. It is disabled when `NODE_ENV=production`.

## 7. Deployment

| Component | Production | Local |
|---|---|---|
| Next.js | Vercel | `next dev` |
| catalog-service | Docker on a 16 GB VPS, behind Caddy (automatic HTTPS) | Docker Compose |
| Elasticsearch 9 | Same VPS, single node, security enabled, not publicly exposed | Docker Compose |
| MySQL 8 | Managed (DigitalOcean Managed DB or AWS RDS), automated backups and point-in-time restore | Docker Compose |
| Images | Cloudflare R2 + CDN | MinIO in Docker Compose |

- **Estimated cost:** about US$40–80/month at launch. Verify current prices before purchasing.
- **Environments:** local, staging (same setup as production, with seed data), and production.
- **Configuration:** everything comes from environment variables, so moving to AWS later needs no code changes.

## 8. Security

- HTTPS everywhere. MySQL and Elasticsearch are reachable only on the private network.
- Secrets are supplied only through environment variables. Rotate the committed MySQL password.
- JWT validation and role checks on `/api/v1/admin/**`. Public GET endpoints are open.
- CORS is restricted to the storefront origin.
- Caddy rate-limits `/search` and `/search/suggest` to 20 requests per second per IP.
- Bean Validation on all request bodies, and a page size cap of 100.
- Descriptions are stored as Markdown and rendered with HTML sanitization.
- Upload restrictions are as in 4.2.
- Dependabot is enabled on both repos.

## 9. Operations

- **Health:** Actuator liveness and readiness checks, with readiness covering MySQL and Elasticsearch.
- **Metrics (Micrometer/Prometheus):** request latency and error rate, search latency, outbox pending count, oldest pending age, failed count, indexer batch duration.
- **Alerts:**
  - more than 1,000 pending outbox rows, or the oldest pending row older than 5 minutes
  - any `FAILED` outbox rows
  - 5xx rate above 1% for 5 minutes
  - Elasticsearch readiness down
- **Logs:** structured JSON with a request ID, propagated from Next.js through the `X-Request-Id` header.
- **Backups:** MySQL is backed up by the managed service. A test restore is required before launch. Elasticsearch is not backed up; it is rebuilt by reindexing.
- **Migrations:** Flyway runs on startup. Each migration must stay compatible with the previous app version, so a deploy can be rolled back.
- **CI/CD (GitHub Actions):**
  - every PR: build, all tests, lint
  - merge to `main`: build the image and deploy to staging
  - production: manual approval

## 11. Build order

1. **Foundation:** Flyway and the new schema, BigDecimal prices, generated IDs, remove FakeStore, ProblemDetail errors, Testcontainers, secrets moved to environment variables.
2. **Catalog admin APIs:** categories, products, variants, specs, publish rules, JWT with dev tokens.
3. **Public APIs:** category tree, category detail, product detail.
4. **Search:** index mapping and analyzers, outbox and indexer, category listing and search, suggest, reindex, degraded mode.
5. **Images:** pre-signed uploads to R2/MinIO and image management.
6. **Next.js storefront.**
7. **Next.js admin.**
8. **Launch readiness:** metrics and alerts, CI/CD, staging, k6 load test, backup restore test, launch checklist.
